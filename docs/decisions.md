# Decisions about these skills

Decisions about the skills repository itself: what it contains, how it is laid out and how it is checked. Decisions about the generated backend are architecture decision records inside the template: `_temp/template/assets/csharp/docs/adr/` (0001 the command dispatcher, 0002 commands as records with interfaces, 0003 the user on the command, 0004 event handlers, 0005 the Console).

## Decided

| # | Decision | Why |
|---|---|---|
| 1 | The generated code follows a fixed set of rules and build guards (banned APIs, no comments in code, no private methods in services and handlers, explicit registration, tests that hold only `[Fact]` / `[Theory]`). | They were learned the hard way and are cheap to enforce from the first day. |
| 2 | The stack is .NET 10, EF Core and PostgreSQL, with our own command pipeline and no mediator library. Code and messages are English. | One stack done well. A mediator would add a dependency for what `CommandPipeline` and `CommandDispatcher` already do. |
| 3 | A skill is `SKILL.md` plus `references/`. `mortis-scaffold` has one folder per language under `references/<language>/`: a naming table, a file manifest, a kernel shape file, and one page per concern with contracts, rules and member snippets. | `SKILL.md` stays short; Claude reads only the page a step needs. |
| 4 | A project is generated, not copied: `mortis-scaffold` writes every file from `references/<language>/` in a numbered procedure and proves it with `scripts/verify.sh` (structure against the manifest, kernel shape, house rules, build, tests, conformance). Replaces the copied `assets/csharp/` solution and `scaffold.sh` (kept only in `_temp/template/` as source material until phase 2). | Decision 13; the knowledge must be enough on its own, and the checks prove it. |
| 5 | The template compiles and is tested as it is. `tests/smoke.sh` scaffolds three solutions (with example, `--no-example`, `--kernel-only`) and checks them against a real PostgreSQL. `tests/check_docs.py` fails when a reference names a file or type that does not exist, or the overview omits a template source file. | The documentation is only trustworthy if a change cannot leave it behind. |
| 6 | Event handlers have two kinds, sync (inside the transaction, can veto) and async (after the commit, eventually consistent), both in the Application layer, both sending commands. | The reaction to an event must run a use case; see ADR 0004. |
| 7 | "Use case" is called "command". A host sends a command through `ICommandDispatcher` and never names its handler. Commands are records that implement `ICommand<TContent>`, `IUserCommand` and `ITransactionalCommand`; the user is data on the command, filled by the presentation layer. | ADRs 0001 to 0003. |
| 8 | The Console runs any registered command by name and does not migrate. Migrations are `dotnet ef database update`. | ADR 0005. |
| 9 | Work is done in phases. Phase 1 (`mortis-scaffold`) is complete. | One tested thing at a time. |
| 10 | The assistant does not commit. The maintainer reviews and commits. | The maintainer owns the history. |
| 11 | A small change is made at once; a big one gets a plan first. | Keeps the maintainer in control of direction. |
| 12 | The repository is a **project starter**: a person chooses methods and technologies in an interview and gets exactly that, lean or advanced. The choices live in `MORTIS.md`. | One fixed template cannot serve both a weekend service and a platform. See `options-catalog.md`. |
| 13 | **The skills hold knowledge and checks, never a project.** Claude writes a user's project from the references; the solutions in this repository are reference examples under `examples/`, used to verify the skills and not installed. Three layers (architecture in pseudo-code, language, proof); four skills named `mortis-architect`, `mortis-scaffold`, `mortis-develop`, `mortis-review`. From phase 1 step 03 on this replaces decision 4, and it replaces the earlier idea of a core plus modules copied by a script. | A starter that ships a template can only produce that template. `specs/generation-and-verification.md`. |
| 14 | Event delivery has exactly three models: `none`, `after-command`, `background`. | The maintainer's requirement; the last two share one module. |
| 15 | Our own message bus, wire-compatible with MassTransit 8 on RabbitMQ. Not MassTransit 9 (commercial), not MassTransit 8 (maintenance ends after 2026), not OpenTransit (no releases yet, .NET only). | Existing MassTransit consumers must keep working and Go must speak the same format. `specs/messaging-wire-format.md`. |
| 16 | Multi-tenancy is one shared database with `IMultiTenant` on the aggregates and entities that are tenant-owned. A database or schema per tenant is not offered. | A database per tenant is exceptional and multiplies migrations and connection handling. |
| 17 | The steps are prepared as briefs in `plans/`; a coding model executes them. | The maintainer's choice of how to work. |
| 18 | The product, repository and plugin are named **mortis-starter**; the skills keep the names in decision 13. | Domain-driven design is one part of what the starter sets up. |
| 19 | The finished skills hold snippets, never whole source files. Full source exists only in `examples/` while the skills are built. | The skills are knowledge, not a template. |
| 20 | Generation must succeed on small models as well as large ones, and runs must be alike: a file manifest, a kernel shape file, a closed vocabulary, one way per thing, tools for what tools can do, and a measured sameness report. | `specs/generation-and-verification.md`, "Making runs alike". |
| 21 | No document or skill names a codebase that was studied. Origins are kept only in `_sources/`, which is ignored by git and deleted at the end. | The product stands on its own. |
| 22 | A command carries one `Context` property (user, correlation, tenant, language). The tenant id type is chosen per project. Generated Go has doc comments on exported names only. | Settled before coding started. |
| 23 | Naming follows the chosen language; layer 1 names roles and each language has its own naming table. Database, JSON, route and event naming are project choices in `MORTIS.md` that the interview may ask. | A Go project must read as Go and a C# project as C#. |
| 24 | Languages are pluggable: references, one adapter script per skill, and examples. C# first, Go second, others later without changing the language-neutral parts. | More languages are expected. |
| 25 | A project's decisions are recorded in `MORTIS.md` in its root: markdown for readers and assistants, with one fixed table that scripts read. | It sits among the project's other markdown, explains itself, and points at the skills; one file cannot drift from itself. |
| 26 | Three phases: build all the skills with no code generated; generate C# together with the maintainer; then Go. Code is never generated per option. | Generation costs tokens; a few runs that each exercise many options are enough. The accepted price: nothing is proven until phase 2, so everything written in phase 1 is listed in `docs/unverified.md`. |
| 27 | The hand-written C# solution and its copy script live in `_temp/template/`, outside the skill, until phase 2 replaces them with generated projects. | The skill must hold no project source, and the working code is still needed to write the kernel pages from. |

| 28 | The command handler is the use case (application service): it loads the aggregates one action needs, calls their operations or a domain service, and saves. It may change several aggregates when the action is about all of them (the test: without the second change, does the command still do what its name says?); a consequence of the action is an event handler. A domain service holds logic that fits no single aggregate: it may load several entities and call other systems through anti-corruption layers. | Replaces the template's rule "a handler calls one method of the aggregate's service". Maintainer's decision, 2026-11-17. No `*Service` per aggregate: handlers load and save; a domain service decides and reads, the command handler saves what it changed. |
| 29 | The standard preset has `languages.mode` = `none`; translated messages are asked only when the description mentions languages. | An eval showed the default surprised users who never asked for translations. |
| 30 | One repository is one service, with one `MORTIS.md` in its root. A platform of several services is several repositories, each started with its own interview; shared choices (broker, tenancy, wire naming) are repeated in each file. | The maintainer keeps every service in its own repository; the shared wire format keeps the services compatible. |
| 31 | A domain service is pure by default (the command handler passes in what it loaded). It may read through an interface declared in Domain, a narrow read port in preference to a whole repository, when the rule decides what data it needs. It never writes: no create, update, upsert or delete, no save, no commit, no transaction. The command handler owns every write and the commit. `verify.sh` fails a write call or `IUnitOfWork` in the Domain project; `mortis-review` checks the same. | Maintainer's decision, 2026-11-17, after weighing the DDD literature: reads in domain services are a team choice, writes in them split persistence across two classes and make a write's timing depend on infrastructure. |
| 32 | Error handling has three levels with one error body and the same statuses at every level (404, 422, 409, 500; 409 `duplicate` and 400 `reference_violation` from `coded` up). `minimal` leaves out only the translation of database errors (they are 500); `coded` adds it; `catalogued` adds a catalogue of every code with its default message and a test. Every level logs 4xx as a warning and 5xx as an error and answers an unexpected failure with a reference. The `errors` field stays `{ field: [messages] }`. | Maintainer's answers to step 07, 2026-11-17: moving up a level must never break a client. |
| 33 | A generated project contains only the code of the options in `MORTIS.md`: no code for an option that is off, and no runtime switch between options. Where an option changes a kernel file, the page gives one version per value and the kernel shape marks the lines that differ. | Maintainer's decision, 2026-11-20, after reviewing step 08: the first outbox draft kept every mode in one project behind settings. |
| 34 | The Console is a host that runs one command per run, found by name in the Application assembly; no scenarios, no registration line per command. stdout holds only the result; logs go to stderr. | Maintainer's decision, 2026-11-20: the scenario structure was more code than a manual-test host needs; a flow is a sequence of runs. |
| 35 | Every log line, in every host and environment, is one flat JSON object with `CorrelationId` as its first field, then the fixed fields and every scope and template field at the top level; written by one small formatter class. | Maintainer's decision, 2026-11-20. The built-in JSON formatter nests scope fields, which the maintainer ruled out. |
| 36 | The outbox models share one table and one worker: the row, its async handlers and its deletion are one transaction, claimed with `for update skip locked`; failures count attempts with a backoff and stay at the limit. No inbox, transport seam, lock column or published status until a broker needs them (step 09). `after-command` adds only "publish my own rows after `COMMIT`". | Maintainer's direction, 2026-11-20: "Message, Repo, Worker, as simple as possible". |
| 37 | Three complete reference solutions, one per preset, live in `_temp/variants/{lean,standard,advanced}/`, each with the example and its own `MORTIS.md`. They are the source of truth: the C# pages, the manifest and the kernel shape are extracted from them, and each must build, test and pass `verify.sh` at the end of every step. They are edited directly; `tests/check_variants.py` fails on a difference between them that no option explains, and on a file the manifest places wrongly. They hold only options built so far (later options keep their lean value until their step). The original `_temp/template/` stays untouched; the overlay tooling and the pilot project are removed. Values no preset uses are covered by page snippets only. | Maintainer's decision, 2026-11-20: a choice must exist as code one can open, read and run, not as a patch assembled in a temporary folder. |
| 38 | The RabbitMQ bus (step 09): our own classes on `RabbitMQ.Client` with MassTransit 8's wire format, consuming our own events only (no `IConsumer<T>` for foreign messages yet). It reads MassTransit envelopes from both serializers and writes one format with fanout exchanges (no per-type overrides yet). A receive endpoint is configured in code, never in settings: queue name, retry count and, optionally, the events; without a list it consumes every event that has an async handler. After the retries a message goes to `<queue>_error` with the MassTransit fault headers; a message no handler wants is acknowledged and logged. The interoperability with MassTransit 8.5.12 is proven while the skills are built, by `_temp/interop/`. | Maintainer's answers to step 09's scope, 2026-11-21. |
| 39 | Every async event handler is a consumer of its own, in every publishing model: its own transaction, retries, failure and, with a broker, its own queue (named after the handler in kebab case, without `EventHandler`) and inbox row. `none`: `EventPublisher` already ran each handler alone. `database` outbox: one row per event and handler. `rabbitmq`: one outbox row per event, one receive endpoint per handler (`AddEventConsumers`), configured in code. Supersedes the "one transaction for all handlers of a row or message" of decisions 36 and 38. | Maintainer's direction, 2026-11-21: "Every IAsyncEventHandler is an EventConsumer, treat it as such." |
| 40 | No inbox. With RabbitMQ a message can reach a handler twice; every async handler must be safe to run twice, and a handler that needs deduplication keeps its own record in its own transaction. The bus stays a transaction around the handler. Supersedes the inbox of decisions 38 and 39. | Maintainer's decision, 2026-11-21: "extra complexity, the developer can handle that in their async event handler." |
| 41 | An async event handler is an **event consumer**: `BaseEventConsumer<TEvent>`/`IEventConsumer`, named `{Action}When{Aggregate}{Event}EventConsumer` (its queue drops `EventConsumer`). The only way to register one is an explicit line in the host that runs it, `AddEventConsumer<TConsumer>(endpoint => endpoint.Retry(3))`: the Api and the Console with `in-process` or `database`, the Worker with `rabbitmq`. `ApplicationModule` registers no consumer and nothing is discovered by scanning. `Retry(n)` (n retries after the first attempt) and `Named(queue)` are per consumer in every model and replace `MessagingConstants.MaxAttempts` and `OutboxSettings.MaxAttempts`: `none` retries any failure in a fresh scope; a `database` row carries `max_attempts`; `rabbitmq` retries, then `<queue>_error`, while the outbox retries publishing until the broker takes it (backoff capped by `OutboxSettings.MaxBackoffSeconds`). Consumers run in the order of their lines (`Sequence` is gone from consumers). Supersedes the discovery (`AddEventConsumers`) and the global retry settings of decisions 36, 38 and 39. | Maintainer's direction, 2026-11-21: "rename AsyncEventHandlers as EventConsumers. Only allow this approach", with the answers "in the host that runs them" and "per consumer everywhere". |
| 42 | Step 10 (testing levels) is skipped for now and step 11 comes next. The tenant is the signed-in user's `tenant_id` claim, in the Api and the Console alike, so step 15's sign-in part is built inside step 11: JWT bearer validation (an OpenID Connect authority, or a development signing key in Development only), claim names as settings, every controller behind a signed-in caller except `/health`, the Console reading the same token from `--token` or `MORTIS_TOKEN` (no token: the console user, no tenant), and a `dev-token` Console command that refuses outside Development. Built in standard and advanced, whose presets have `auth` = `jwt` (decision 37). Permissions (`IAuthorizedCommand`) stay in step 15. New rule R13: `tenancy.mode` = `interface` requires `auth` = `jwt`. | Maintainer's answers to step 11's scope, 2026-11-22: "Logged in User's TenantId" for the Api and the Console; "Pull step 15's sign-in into 11"; "A token passed to the run". |
| 43 | Multi-tenancy (step 11), built in the advanced variant with `tenancy.key` = `guid` and `tenancy.resolver` = `claim`: `IMultiTenant { Guid TenantId }` on tenant-owned types (no `TenantId` wrapper type: with decision 33 the chosen key's type is used directly, `text` is a page note); a scoped `TenantScope` entered by the Api filter, the Console and each consumer before any service is resolved, and checked by a pipeline middleware; a query filter per tenant-owned type and stamping in `SaveChangesAsync`; a missing tenant is 403 `tenant_required` before any SQL, another tenant's row is not found; unique keys and foreign keys between tenant-owned tables start with `tenant_id`; the outbox row stores the event's tenant; `TenantScope.Bypass` is the one logged way past the filter. `header` and `subdomain` resolvers, `text` keys and tenancy with `in-process` or `database` transports are page knowledge only. | Maintainer's answers to step 11's scope, 2026-11-22: "Fail, 403"; "Scoped TenantScope, as planned". |
