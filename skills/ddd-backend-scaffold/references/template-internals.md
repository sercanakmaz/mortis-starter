# How the template is built, and how to change it safely

## Layout

```
assets/csharp/            one complete solution named "Boilerplate", example included
assets/csharp-example.txt the list of what makes up the example
scripts/scaffold.sh
```

There is one folder per language and nothing else to keep in step with it. The solution in `assets/csharp/` builds and passes its tests as it is: it contains the Order / Customer / Product example, its migration and its tests.

`scaffold.sh` copies the folder, and with `--no-example` removes the example using `csharp-example.txt`. Then it renames: every `Boilerplate` in file names and file contents becomes the solution name, and every lowercase `boilerplate` becomes the lowercased name with dots turned into underscores. `--lang` picks the folder (`csharp` is the only one today); `--kernel-only` copies only `Boilerplate.Shared` and the build guards.

Two consequences:

- **The solution compiles as it is.** Because the placeholder is a real name, you can open `assets/csharp` as a solution, build it and run its tests while you work on it.
- **Never write the word "boilerplate" in a file unless you mean the placeholder.** It will be replaced.

## The example manifest

`csharp-example.txt` has one instruction per line:

| Line | Meaning |
|---|---|
| `delete <path>` | Remove a file or folder. Used for every example aggregate folder, command folder, controller, repository, migration, scenario and test. |
| `lines <pattern> <file>` | Drop every line of a registration file that matches the pattern, then tidy blank lines. Used for `DomainModule.cs`, `PersistenceModule.cs`, `ApplicationModule.cs` and `ScenarioModule.cs`, because registration is explicit and those four files list the example's handlers and modules. |
| `launch <pattern> <file>` | Remove the `launch.json` configurations whose name matches. |

When you add an example file under an existing example folder, nothing changes. When you add a new example folder, add a `delete` line for it; when you register something new in one of the four module files, make sure its line contains a word the pattern matches (`Customer`, `Order`, `Product`, `Completed`, `LineAdded`, `LineCancelled`, `StockFlow`), or extend the pattern. `tests/smoke.sh` builds the `--no-example` output and fails if any example code is left behind or the result does not build with 0 warnings.

## The migration

`assets/csharp/src/Boilerplate.Infrastructure/Persistence/Migrations/` was generated by `dotnet ef migrations add Initial`. After changing an aggregate or its EF configuration, regenerate it rather than editing it by hand:

1. Copy `assets/csharp/` into a temporary folder, **without** renaming.
2. Delete `Persistence/Migrations` there, run `dotnet build`, then `dotnet ef migrations add Initial --project src/Boilerplate.Infrastructure --output-dir Persistence/Migrations`.
3. Copy the three generated files back into `assets/csharp/...`.

## Proving a change

`tests/smoke.sh` in the skills repository scaffolds three solutions (with the example, with `--no-example`, and `--kernel-only`) and checks them end to end against a real PostgreSQL: build, tests, the banned-API guard, migrations, the Console scenarios and commands with the resulting rows read back from the database, the Api's status codes and error bodies, and concurrent stock updates.

```bash
PGHOST=localhost PGUSER=postgres PGPASSWORD=postgres bash tests/smoke.sh
```

The script also runs `tests/check_docs.py`, which compares these references with the template. A change is done when the script prints `0 failed`. If you add behaviour, add the check for it to the script in the same change.
