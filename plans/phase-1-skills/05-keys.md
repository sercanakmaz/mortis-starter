# Phase 1, step 05 — Key types per aggregate (knowledge only)

Needs: phase 1 steps 03. Size: small. Changes the kernel pages. No C# is written, built or generated in this step.

## Goal

`Entity<TKey>` and `IRepository<TAggregate, TKey>` are already generic, but only `Guid` keys are exercised. Make integer keys generated by the database a supported, tested choice per aggregate, and write down what changes when the id is unknown until the insert.

## Design

| Key | Who assigns it | When it is known |
|---|---|---|
| `Guid` (version 7) | the aggregate's constructor, or the client | before the insert |
| `int` / `long` identity | the database | after the insert |

- `MORTIS.md` `keys.default` picks what new aggregates get by default; any aggregate may differ.
- EF configuration: a base configuration for identity keys (`ValueGeneratedOnAdd`); the existing one for `Guid` stays `ValueGeneratedNever`.
- **Events and database-assigned ids.** An aggregate with an identity key must not put `Id` into an event it raises in its constructor. Pattern: the constructor raises nothing; the service calls `repository.CreateAsync(aggregate)` (which saves, so the id exists) and then `aggregate.MarkCreated(user)`, which raises `Created` with the real id. Document it in the architecture layer as a rule of the key choice, with the reason.
- A client cannot supply the id of such an aggregate; its create command has no `Id` property.
- Foreign keys to it are `int` / `long`.
- Example: add a small `Category` aggregate with an `int` key that `Product` may reference (`CategoryId`, nullable). It belongs to the example domain, so it is added to `example-domain.md` and appears only when the example is on.

## Out of scope

Strongly typed id wrappers, string keys, MongoDB ids (step 13).

## Traps

`CreateAsync` must flush for the id to exist. If the repository today defers the insert to commit, change it for identity keys only and say so in the reference; statement order is then part of the behaviour.

## Notes (done)

- Kernel: `ConfigurationExtensions.IdentityAggregateConfiguration<TAggregate, TKey>` (the aggregate configuration plus `ValueGeneratedOnAdd()`). Nothing else in the kernel changes: `Entity<TKey>`, `IRepository<TAggregate, TKey>` and `EfRepository` were already generic, and `CreateAsync` already flushes at once, so the trap does not bite.
- Pattern (decision 28 puts it in the handler, not a service): construct (raises nothing), `CreateAsync`, `MarkCreated()` (raises `Created` with the real id), `UpdateAsync` to hand the event over, all in the command's transaction.
- Example: `Category` with an `int` key, `CreateCategory`, `GetCategory`, `CategoriesController`, and an optional `Product.CategoryId` (an optional last constructor parameter, so no existing call changes). Domain, handler and configuration tests; the test repository builder assigns the id the way the database would.
- ADR 0008 for every generated project; `AGENTS.md` §3 mentions the rule.
- Conformance: two database checks (identity column, the optional foreign key) and five HTTP checks; the table list now includes `categories`.
- Not covered: a project with `keys.default` = `int` and no example changes nothing in the kernel; it matters when `mortis-develop` adds an aggregate (step 17).
