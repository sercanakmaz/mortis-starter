- mortis-architect: Interviews the person starting a backend project and writes MORTIS.md, the decisions file every later step reads. Picks a lean, standard or advanced preset from the description, asks only about what is doubtful (outbox and event delivery, broker, multi-tenancy, translated messages, exceptions, queries, testing, authentication, naming), refuses combinations that cannot work, and records a decision for every change from the preset. Also explains where code belongs (layers, aggregates, commands, events). Use whenever someone wants to start, plan, bootstrap or architect a new backend, API or service, asks which outbox, broker or tenancy model to choose, asks "where does this code go", or says "lean", "standard" or "advanced" project, even when they never mention DDD.
- mortis-scaffold: Generates a new backend project from its MORTIS.md decisions file, writing every file from the skill's reference pages (contracts, rules and member snippets), then proves it with verify.sh (structure, kernel shape, house rules, build, tests and behaviour checks against a real database). Also brings the building blocks into an existing solution. C# (.NET 10, EF Core, PostgreSQL) for every preset; Go (pgx, PostgreSQL) for the lean preset. Use whenever the user wants to create, generate, scaffold or bootstrap a backend, API or service, has a MORTIS.md and asks to build it, asks for a .NET "starter", "boilerplate" or "clean / DDD structure", or wants an existing solution to adopt this structure, even if they never say "scaffold".
- mortis-develop: Adds things to a project that mortis-scaffold generated, the way its MORTIS.md decisions require - an aggregate, a child entity, a value object, a command, a query, an event, a sync or async handler, an event consumer, a read model, a tenant-owned aggregate, a translated field, a key type change - and turns an option on later (add the outbox, tenancy, an add-on). Follows a recipe per request, test first, touching every file the change needs and nothing else, then runs verify.sh. Use whenever someone asks to add, extend, change or implement something in a Mortis project (a project with a MORTIS.md), asks "where else must this change", or wants to switch an option on after the project exists, even if they never name the skill.
- mortis-review: Reviews a change or a whole Mortis project (a project with a MORTIS.md) against its rules - runs review.sh for the mechanical checks (comments, private helpers in handlers, rules outside the aggregate, hosts naming handlers, missing registrations, writing commands without a context, tenant-less unique indexes, reactions that inject repositories, helpers in test classes, banned APIs, queue-event contracts, writes in the domain, cross-context references), then walks the judgement checklist the script cannot do, and reports findings with file, line, rule and a concrete fix, most severe first. Use whenever someone asks to review, check, audit or "look over" code, a diff, a branch or a pull request in a Mortis project, or asks whether a change follows the project's rules, even if they never name the skill.
- code-review: Reviews code changes for bugs, security issues and style in any language. Use when the user asks for a code review of a diff, file or pull request.
- frontend-design: Guidance for distinctive visual design when building new UI or reshaping an existing one.
- xlsx: Use this skill any time a spreadsheet file is the primary input or output.
- docx: Use this skill whenever the user wants to create, read, edit, or manipulate Word documents.
- pdf: Use this skill whenever the user wants to do anything with PDF files.
- deep-research: Use when the prompt requires researching a topic across multiple sources and synthesizing a report.
- debugging: Systematic debugging of failing tests, crashes and performance problems in any codebase.
- dotnet-upgrade: Upgrades .NET projects between framework versions: target frameworks, package versions, breaking changes.
